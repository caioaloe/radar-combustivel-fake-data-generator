1 Descrição do Problema

A plataforma Radar Combustível monitora preços de combustíveis em postos de abastecimento em todo o Brasil. Usuários consultam o aplicativo para encontrar o posto mais barato próximo à sua localização, acompanhar variações de preço e registrar avaliações.

O desafio técnico consiste em transformar dados transacionais armazenados no MongoDB em uma camada de consulta de baixíssima latência no Redis, capaz de responder em tempo real a perguntas como:

  • Quais postos estão com menor preço de Gasolina Comum em São Paulo?
  • Quais combustíveis tiveram maior variação de preço esta semana?
  • Quais cidades apresentam maior volume de buscas na plataforma?
  • Quais postos existem em um raio de 50 km da minha localização?
  • Como evoluiu o preço médio do Etanol em Minas Gerais nos últimos 90 dias?
Decisão de recorte: o grupo focou nas consultas de maior valor analítico para o usuário final — ranking de preços, busca geográfica e série temporal de preços — implementando tanto atualização em lote (batch) quanto orientada a eventos (Change Stream), o que permite demonstrar os dois modelos de pipeline na apresentação.

2 Arquitetura da Solução

A solução é composta por quatro camadas executadas em contêineres Docker:

┌──────────────────────────────────────────────────────────────────────┐ │ Docker Compose │ │ │ │ ┌──────────────────┐ ┌────────────────────────┐ ┌───────────┐ │ │ │ MongoDB 7 │ │ pipeline_radar.py │ │ Redis │ │ │ │ Replica Set │──▶│ │──▶│ Stack │ │ │ │ rs0 │ │ ① Fase Batch │ │ │ │ │ │ │ │ Agrega MongoDB │ │ HASH │ │ │ │ postos │ │ Popula Redis │ │ ZSET │ │ │ │ eventos_preco │◀──│ │ │ GEO │ │ │ │ buscas_usuarios │ │ ② Change Stream │ │ TimeSeries│ │ │ │ avaliacoes_ │ │ Eventos em real time│ │ │ │ │ │ interacoes │ └────────────────────────┘ └─────┬─────┘ │ │ │ localizacoes_ │ │ │ │ │ postos │ ┌────────▼──────┐ │ │ └──────────────────┘ │ Streamlit │ │ │ │ Dashboard │ │ │ seed_radar_combustivel.py │ :8501 │ │ │ (gerador de dados fake) └───────────────┘ │ └──────────────────────────────────────────────────────────────────────┘

Fluxo de dados

  1. Seed: o script seed_radar_combustivel.py gera 100.000 documentos em cada uma das 5 coleções do MongoDB usando a biblioteca Faker com locale pt_BR.
  2. Fase Batch: o pipeline lê agregações do MongoDB e popula todas as estruturas Redis de uma vez. Duração: ~40 segundos para 500K documentos.
  3. Fase Change Stream: após o batch, o pipeline abre um Change Stream na coleção eventos_preco e atualiza os rankings e a série temporal a cada novo evento inserido, sem reprocessar toda a base.
  4. Serving: o dashboard Streamlit consulta exclusivamente o Redis, garantindo respostas em poucos milissegundos.

3 Pipeline MongoDB → Redis

Fase 1 — Batch

Ao iniciar, o pipeline executa as seguintes etapas em sequência:

① batch_postos

Percorre toda a coleção postos e para cada documento cria um HASH posto:{id} com nome, bandeira, cidade e UF. Simultaneamente adiciona as coordenadas ao índice GEO geo:postos em lotes de 500 para otimizar o throughput.

② batch_rankings_preco

Agrega eventos_preco por posto × combustível, selecionando o preço mais recente de cada par. Para cada resultado usa o HASH já carregado no Redis para descobrir a UF do posto (O(1), sem novo acesso ao MongoDB) e executa ZADD ranking:preco:{combustivel}:{uf} {preco} {posto_id}. Score menor = posto mais barato.

③ batch_rankings_buscas

Agrega buscas_usuarios por cidade/estado e popula o ZSET ranking:buscas com member="cidade|uf" e score=contagem.

④ batch_rankings_variacao

Agrega eventos_preco para obter a variação percentual mais recente de cada posto por combustível. Popula ranking:variacao:{combustivel} com score=|variacao_pct|.

⑤ batch_stats_globais

Calcula mín, médio e máx de preço por combustível em toda a base e armazena no HASH stats:preco_medio.

⑥ batch_timeseries

Agrega eventos_preco por dia × combustível × UF com $lookup em postos e grava a média diária nas chaves de TimeSeries ts:preco_avg:{combustivel}:{uf}.

Saída do batch (produção)

Fase 2 — Change Stream (tempo real)

Após o batch, o pipeline abre um Change Stream na coleção eventos_preco filtrando apenas operações de insert. Para cada novo evento:

  1. Consulta a UF do posto via HGET posto:{id} uf (O(1) no Redis, sem acesso ao MongoDB).
  2. Atualiza ranking:preco:{comb}:{uf} com o novo preço.
  3. Atualiza ranking:variacao:{comb} com a variação absoluta.
  4. Adiciona o ponto à série temporal ts:preco_avg:{comb}:{uf}.
# Trecho do pipeline — handle_novo_evento
def handle_novo_evento(r: Redis, doc: dict) -> None:
    pid   = str(doc.get("posto_id", ""))
    comb  = doc.get("combustivel", "")
    preco = float(doc.get("preco_novo", 0))
    uf    = r.hget(f"posto:{pid}", "uf") or "XX"   # O(1)

    r.zadd(f"ranking:preco:{comb}:{uf}", {pid: preco})
    r.zadd(f"ranking:variacao:{comb}",   {pid: abs(doc["variacao_pct"])})

    ts_ms = int(doc["ocorrido_em"].timestamp() * 1000)
    ts_add(r, f"ts:preco_avg:{comb}:{uf}", ts_ms, preco, {...})

O Change Stream se reconecta automaticamente em caso de falha de rede, com backoff de 3 segundos.

4 Estruturas Redis Utilizadas

HASH — posto:{id}

Justificativa: o HASH é a estrutura ideal para armazenar o cadastro resumido de cada posto. Permite leitura de campos individuais em O(1) sem deserializar o documento inteiro. O pipeline usa esse HASH como lookup cache para evitar joins desnecessários no MongoDB durante o Change Stream.

CampoConteúdoExemplo
nomeNome fantasia do postoPosto Oliveira & Filhos
bandeiraBandeiraShell
cidadeMunicípioCampinas
ufEstadoSP
ativoFlag de status1

GEO — geo:postos

Justificativa: o tipo GEO do Redis permite calcular distâncias e filtrar por raio geográfico em O(N+log M) usando um índice geoespacial interno (geohash). A alternativa seria carregar todas as coordenadas e calcular no Python, o que seria inviável para 100K postos.

# Busca postos em 50 km de São Paulo
GEOSEARCH geo:postos FROMLONLAT -46.6333 -23.5505
          BYRADIUS 50 km ASC COUNT 20 WITHCOORD WITHDIST

ZSET — ranking:preco:{combustivel}:{uf}

Justificativa: o Sorted Set é a estrutura perfeita para rankings. O score armazena o preço atual do posto (menor = mais barato). ZRANGE ... WITHSCORES retorna os N postos mais baratos em O(log N + N), independente do tamanho total do ranking. A separação por combustível e UF permite consultas regionais sem filtros adicionais.

ZSET — ranking:buscas

Justificativa: a contagem de buscas por cidade é um caso de uso clássico de Sorted Set. Score = número de buscas. ZREVRANGE ranking:buscas 0 9 entrega as 10 cidades com maior demanda em O(log N).

ZSET — ranking:variacao:{combustivel}

Justificativa: mede a volatilidade de preços por posto. Score = variação percentual absoluta. Postos com maior oscilação ficam no topo, útil para alertas e monitoramento de mercado.

HASH — stats:preco_medio

Justificativa: armazena estatísticas globais de preço (mín, médio, máx por combustível) calculadas via agregação MongoDB. Serve o painel de resumo do dashboard em uma única chamada HGETALL.

TimeSeries — ts:preco_avg:{combustivel}:{uf}

Justificativa: o módulo RedisTimeSeries (incluído no Redis Stack) armazena séries temporais com compressão nativa e suporte a agregação por janela de tempo sem varrer todos os pontos. Permite responder "qual foi o preço médio diário da Gasolina Comum em SP nos últimos 90 dias?" em uma única chamada TS.RANGE.

TS.RANGE ts:preco_avg:GASOLINA_COMUM:SP - +

Cada série temporal é criada com DUPLICATE_POLICY LAST para aceitar re-inserções idempotentes do batch, e com labels combustivel e uf para consultas multi-série com TS.MRANGE.

6 Decisões Técnicas

DecisãoEscolhaJustificativa
Lookup de UF no Change Stream HGET Redis (O(1)) Evita um novo acesso ao MongoDB por evento, eliminando latência e carga desnecessária na fase stream.
Separação de rankings por UF Chave composta :comb:uf Permite consultas regionais sem filtros pós-leitura; cada ZSET já está pré-filtrado por estado.
TimeSeries por dia Agrega por $dateToString no MongoDB 90 dias × 6 combustíveis × 10 UFs = 5.400 pontos — volume gerenciável com granularidade suficiente para o negócio.
Batch antes do stream Sempre roda batch ao iniciar Garante que o Redis parte de um estado consistente mesmo após reinicializações, sem depender da história do oplog.
Reconexão automática Try/except com sleep(3) O Change Stream pode ser interrompido por failover do replica set; a reconexão automática garante continuidade do serviço.
DUPLICATE_POLICY LAST TimeSeries Permite que o batch seja re-executado de forma idempotente sem duplicar pontos na série temporal.

7 Conclusão

O projeto demonstra um pipeline completo de dados que combina a flexibilidade do MongoDB para armazenamento documental com a velocidade do Redis como camada de serving. A separação em duas fases — batch e Change Stream — permite equilibrar consistência (o batch reprocessa toda a base periodicamente) com latência (o stream atualiza rankings em tempo real a cada novo evento de preço).

As estruturas Redis foram escolhidas especificamente para cada padrão de consulta: ZSET para rankings ordenados, GEO para buscas por proximidade, TimeSeries para evolução temporal e HASH como cache de cadastro. Essa modelagem orientada a acesso é o que permite ao dashboard responder todas as perguntas de negócio sem nenhuma consulta ao MongoDB em tempo de serving.

O resultado é uma plataforma capaz de servir consultas como "top 10 postos mais baratos de Gasolina Comum em SP" ou "postos em 50 km de São Paulo" em poucos milissegundos, independente do volume de dados armazenado no MongoDB.
